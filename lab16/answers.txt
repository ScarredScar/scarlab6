Лабораторная работа №16. Ответы на контрольные вопросы

Вопрос 1. Почему прямая попытка зарегистрировать python.exe script.py через sc create приводит к ошибке Error 1053? Каких действий ждет SCM в первые 30 секунд?

Ошибка 1053 (The service did not respond to the start or control request in a timely fashion) возникает из-за нарушения низкоуровневого протокола взаимодействия с диспетчером SCM (services.exe).
Обычный интерпретатор (python.exe) является консольным приложением Ring 3 и ничего не знает о службах. Если запустить его через SCM, диспетчер ожидает, что процесс в течение 30 секунд вызовет функцию StartServiceCtrlDispatcher() из библиотеки advapi32.dll, чтобы открыть именованный канал (IPC) для общения. Обычный Python этого не делает — он просто пытается выполнить код в консоли. Не дождавшись регистрации по истечении таймаута (30 секунд), SCM принудительно убивает процесс через TerminateProcess с кодом 1053.
Именно поэтому для Python используется обертка pywin32 (win32serviceutil), которая берет на себя вызов нужных API, а уже внутри себя запускает пользовательский скрипт.

Вопрос 2. Почему фоновое задание PowerShell работает в Сессии 0 от имени SYSTEM, но утилита sc query его не видит?

Это архитектурный парадокс разделения подсистем управления фоновыми задачами в Windows:
1. Утилита sc.exe (Service Control) обращается напрямую к базе данных диспетчера SCM (services.exe) в реестре по пути HKLM\SYSTEM\CurrentControlSet\Services\.
2. Мы создавали PowerShell-задачу не через SCM, а через Планировщик заданий (Task Scheduler) с помощью команды schtasks.
Планировщик заданий — это отдельная подсистема Windows (управляется службой Schedule и оснасткой taskschd.msc). Она умеет запускать процессы от имени SYSTEM в Сессии 0 при старте системы, но регистрирует их в своей собственной базе данных (в папке Windows\System32\Tasks), а не в базе SCM.
Поэтому sc query ищет задачу в списке служб, не находит её там и выдает ошибку 1060 (Служба не установлена), хотя процесс powershell.exe физически работает в фоне.

Вопрос 3. Что такое политика выполнения PowerShell (Execution Policy)? Зачем её менять и какие риски это несет?

Execution Policy — это встроенный механизм безопасности PowerShell, который определяет, какие скрипты (.ps1) разрешено запускать в системе. По умолчанию в Windows стоит Restricted (запрещено запускать любые скрипты).
Значение RemoteSigned (которое мы установили) разрешает запуск локальных скриптов без цифровой подписи, но требует подписи для скриптов, скачанных из интернета (имеющих метку зоны).
Зачем менять: Без этого изменения операционная система заблокирует выполнение нашего фонового скрипта win_monitor.ps1.
Риски: Снижение уровня безопасности. Если злоумышленник получит доступ к системе и сможет записать свой вредоносный .ps1 файл локально, система позволит ему выполниться без цифровой подписи, что может привести к заражению (например, через шифровальщики, которые часто используют PowerShell).
